.de 도메인이 통째로 먹통? DNSSEC이 뭔지 이제는 알아야 할 것 같아요

• 독일 최상위 도메인 .de 전체가 DNSSEC 검증 문제로 접속 불가 상태에 빠졌어요. DNS 보안 서명인 RRSIG나 DNSKEY가 잘못 설정되면 도메인 하나가 아니라 TLD 전체가 날아갈 수 있다는 걸 이번 사건이 보여줬죠.
• DNSSEC은 루트 존부터 DS Records로 신뢰 체인을 이어가는 구조예요. 어느 한 고리가 끊기면 하위 도메인 전체가 검증 실패로 응답을 거부당해요. 알고리즘은 RSASHA256(알고리즘 8번)이 주로 쓰이고, 키 교체 타이밍이 특히 위험해요.
• 내가 직접 설정하지 않아도 문제가 생겨요. 도메인 레지스트라나 DNS 호스팅 업체가 키 롤오버를 잘못 처리하면 내 서비스가 피해를 입어요. 모니터링에 DNSSEC 검증 체크를 넣어두는 게 이제는 선택이 아니에요.

💡 오늘의 인사이트

DNS는 '그냥 되는 것'으로 여기기 쉬운데, 이번 사건처럼 보안 레이어가 하나 꼬이면 트래픽 전체가 사라져요. 내 서비스가 .de처럼 피해를 입지 않으려면, 지금 당장 외부 DNS 모니터링 도구에서 DNSSEC 검증 실패 알림을 켜두는 것부터 시작해 보세요. 설정 5분이 장애 대응 5시간을 막아줘요.

LLM 추론 속도 3배, 품질은 그대로? Gemma 4의 다중 토큰 예측이 진짜인지 살펴봤어요

• 구글이 Gemma 4 모델 패밀리에 MTP(Multi-Token Prediction) 드래프터를 공개했어요. Speculative Decoding 구조로 가벼운 드래프터 모델이 먼저 여러 토큰을 예측하고, 메인 모델이 검증만 하는 방식이에요. 결과적으로 토큰 생성 속도가 최대 3배 빨라지고 품질 저하는 없다고 해요.
• 핵심은 KV Cache 공유예요. 드래프터와 메인 모델이 컨텍스트를 다시 계산하지 않고 캐시를 함께 써서 메모리 대역폭 병목을 줄여요. Apple Silicon과 NVIDIA A100에서 배치 크기 4~8 기준으로 최대 2.2배 추가 속도 향상도 확인됐어요.
• vLLM, SGLang, Ollama, Hugging Face Transformers, LiteRT-LM, MLX 등 주요 추론 프레임워크를 모두 지원하고 Apache 2.0 라이선스로 풀렸어요. 지금 쓰는 스택에 바로 붙여볼 수 있어요.

💡 오늘의 인사이트

LLM 서빙 비용 때문에 고민 중이라면 MTP 드래프터를 한번 테스트해볼 가치가 있어요. 품질을 희생하지 않고 처리량을 늘리는 건 쉽지 않은데, 이번 접근은 구조적으로 납득이 가요. 특히 Ollama나 vLLM을 이미 쓰고 있다면 설정 몇 줄로 바로 붙여볼 수 있으니 벤치마크 한번 돌려보는 게 어떨까요.

600달러 들여 만든 소프트웨어를 그냥 공짜로 줬어요. 후회하냐고요? 전혀요

• 오픈소스 퍼즐 앱 Nonograph를 만든 개발자는 보안 리뷰 포함 약 600달러를 들여 앱을 출시하고, 월 5달러짜리 호스팅으로 하루 수십만 명에게 서비스하고 있어요. 구독 결제 인프라를 붙이지 않은 이유는 딱 하나, 비용을 올리고 싶지 않아서예요.
• 이 개발자의 주장은 명확해요. 수익화 순간 사이드 프로젝트는 할당량을 채워야 하는 일이 되고, 사용자에게 불편한 기능이 들어가기 시작한다고요. 열정으로 만든 소프트웨어가 더 좋은 소프트웨어가 된다는 걸 직접 경험으로 증명했어요.
• 대부분의 소프트웨어 프로젝트는 대규모 엔지니어링 팀이 필요하지 않아요. 작게, 가볍게, 내가 즐길 수 있는 범위에서 만드는 것 자체가 가치 있다는 관점이에요. 모든 코드가 스타트업이나 수익 모델로 이어져야 하는 건 아니니까요.

💡 오늘의 인사이트

사이드 프로젝트를 시작했다가 '이걸로 돈을 벌어야 하나' 고민하다 흐지부지된 경험, 다들 한 번쯤 있죠. 이 글은 그 압박에서 벗어나도 괜찮다고 말해줘요. 재미로 만든 것, 그냥 공유하고 싶어서 올린 것, 그것만으로도 충분해요. 지금 서랍 속에 잠들어 있는 그 프로젝트, 완벽하지 않아도 한번 꺼내보는 게 어떨까요.
